# Commodore 64

The C64's CPU is a **6510**: a 6502 with a processor port at `$00`/`$01`. This lane reads a program the user owns, follows it through a BASIC stub and an unpacker when it can, and hands each reached routine to the assembly track. There is no C to match.

## Containers

Each file inside a container is a block: a load address, the bytes, a type and a name.

- **PRG** (`.prg`, and a `C64File` / P00 wrapper). The first two bytes are the little-endian load address. The rest is the file.
- **T64**. The signature is `C64 tape image file`. Directory entries carry the start and end address. The payload does **not** include the two-byte PRG header.
- **D64**. A 35- or 40-track 1541 image (174848, 175531, 196608 or 197376 bytes). The BAM at track 18 sector 0 is `A` `2`. Closed files only. A PRG's load address is the first two data bytes. The last sector's second byte is the valid count, including the two link bytes.
- **G64**. Best effort. Half-tracks are skipped. Track 18 is read for the directory, then file chains from the tracks the GCR decoder can see. A layout it cannot decode is reported, not guessed.
- **TAP** (version 0 and 1). KERNAL pulses: short, medium, long, odd parity, header and data each written twice. A turbo loader is not this format. `tapclean file.tap -doprg` is optional and external; import the PRG it writes. The app does not require tapclean.
- **CRT**. `C64 CARTRIDGE`, then CHIP packets. A cartridge whose bytes at the load address contain `CBM80` is entered at the cold-start vector in the first two bytes. That path is static: the cartridge is not emulated.

The primary block is the first one with a SYS, or the cartridge entry. What the rest of the app stores is a **C64R** image: 64 bytes of header, then 64 KiB of RAM. A function's file offset is `64 + CPU address`.

## BASIC V2

The line list is walked from the load address and detokenised. A next-line pointer is trusted only when it lands on a line whose own link is zero or moves strictly forward inside the buffer. A stale pointer (one that lands on the high byte of the end marker, or anywhere else that is not a line) is ignored and the walk continues after the line's terminating zero. Loops stop the walk.

**Only SYS is a machine-code address.** Spaces and one opening parenthesis are allowed (`SYS 2061`, `SYS(2061)`). RUN's number is a line number. LOAD's operand is a filename. A SYS inside quotes is not an address.

## Following the unpacker

Execution starts at the SYS target (or the first byte after BASIC, or the load address). py65 runs the 6502. The processor port is modelled:

- `$00` is the data direction, `$01` the port. At reset the direction is `$2F` and the port is `$37`.
- The low three bits are LORAM, HIRAM and CHAREN. With `$01 = $37`, BASIC is at `$A000–$BFFF`, I/O at `$D000–$DFFF` and the KERNAL at `$E000–$FFFF`.
- A write to a ROM window hits the RAM under it. A write to I/O, while I/O is mapped, does not touch that RAM.
- This tree does not ship the copyrighted ROMs. A read of mapped BASIC or KERNAL returns `RTS`. A `JSR` into that ROM is skipped. A `JMP` into it stops the run.

A jump or `JSR` into memory just written, whose bytes are a contiguous slice of the loaded file at least 16 bytes long, and while fewer than 1024 new bytes have been written, is a relocated loader (the usual copy onto the stack page). The run continues. Once a lot of memory has been written, the next jump out of that loader to bytes that are not still the original loaded byte is the unpacked entry.

When emulation cannot get there — no loader behaviour in the first 2000 instructions, `BRK`, an illegal opcode, a jump into ROM, or the instruction cap — the SYS address stays the entry and the import note says the method is **static**. An emulated unpack says **emulated** and names the entry.

## Functions

From the real entry the trace follows `JSR` and absolute `JMP`, and the vectors at `$0314` / `$0316` / `$0318` (CINV, CBINV, NMINV) and `$FFFA` / `$FFFC` / `$FFFE`, including pointers the program plants with an immediate load and a store. Calls into the KERNAL and BASIC ROM are named externals (`jsr CHROUT`), not function bodies. A store to a ROM address is a store to RAM under the ROM, so it stays a number.

Indirect `JMP` and `RTS`-dispatch are approximate: a routine reached only that way may be missing. The relocated decruncher is not itself a function start. Data a short branch skips is kept out of the instruction stream and recorded as data.

## Labels

Import writes the memory map into `context.h` and the project symbols, and the disassembly uses those names.

- Processor port `$00` / `$01`, zero page and the usual page-2 and page-3 locations.
- VIC-II `$D000–$D02E` and its mirrors through `$D3FF`. SID `$D400–$D41C` and its mirrors through `$D7FF`. Colour RAM `$D800–$DBFF`. CIA1 `$DC00–$DC0F` and CIA2 `$DD00–$DD0F`, each register named, and their mirrors.
- Default screen RAM `$0400`.
- The KERNAL jump table `$FF81–$FFF3` (`CHROUT` at `$FFD2`, `GETIN` at `$FFE4`, `SETLFS`, `SETNAM`, `LOAD`, `SAVE`).
- BASIC and KERNAL ROM routines and data tables, with a one-line description.

Those ROM names and descriptions come from sk6502 (Richard Dymond, ISC). sk6502's control file derives the annotations from Lee Davison's 2012 disassembly. I/O and zero-page names are the standard map. The header states the assumed banking: **`$01 = $37`**.

## Documenting a routine

`claim_function(track="asm")`. The routine is py65 assembly that rebuilds the snapshot's bytes. Guide `asm` lists the six checks; on this platform:

- `lda #$00`, `sta VIC_BORDERCOLOR`, `jsr CHROUT`, `bne loop`, `.byte` / `.word`.
- Name an address with `wName = $033C`. Hardware and KERNAL/BASIC calls use the map's names.
- `.org`, `.include` and macros are refused.
- A comment before the routine says what it does. The label is not `func_....`.

cc65 is not used to match these programs. A C toolchain is not required to import.
