# Commodore 64

The C64's CPU is a **6510**: a 6502 with a processor port at `$00`/`$01`. This lane reads a program the user owns, takes the memory it ends up in, finds its routines statically and hands each one to the assembly track. There is no C to match.

## Containers

Each file inside a container is a block: a load address, the bytes, a type and a name.

- **PRG** (`.prg`, and a `C64File` / P00 wrapper). The first two bytes are the little-endian load address. The rest is the file.
- **T64**. The signature is `C64 tape image file`. Directory entries carry the start and end address. The payload does **not** include the two-byte PRG header.
- **D64**. A 35- or 40-track 1541 image (174848, 175531, 196608 or 197376 bytes). The BAM at track 18 sector 0 is `A` `2`. Closed files only. A PRG's load address is the first two data bytes. The last sector's second byte is the valid count, including the two link bytes.
- **G64**. Best effort. Half-tracks are skipped. Track 18 is read for the directory, then file chains from the tracks the GCR decoder can see. A layout it cannot decode is reported, not guessed.
- **TAP** (version 0 and 1). KERNAL pulses: short, medium, long, odd parity, header and data each written twice. A turbo loader is not this format. `tapclean file.tap -doprg` is optional and external; import the PRG it writes. The app does not require tapclean.
- **CRT**. `C64 CARTRIDGE`, then CHIP packets. A cartridge whose bytes at the load address contain `CBM80` is entered at the cold-start vector in the first two bytes. That path is static: the cartridge is not emulated.

The primary block is the first one with a SYS, or the cartridge entry. What the rest of the app stores is a **C64R** image: 64 bytes of header, then 64 KiB of RAM. A function's file offset is `64 + CPU address`.

## BASIC V2

The program's BASIC is set aside when the project is made: it is not a function, and `read_data` does not read it. If you still come across bytes that look like a BASIC listing (line links, tokens such as `$9E` for SYS, PETSCII text ending in a zero), it is not machine code: don't document it; remove it with `delete_function(function, reason)` and a sentence saying why.

## Where the memory comes from

A tape is loaded in VICE (the app installs it the first time it's needed). Once the tape has stopped for a while, all 64 KiB of RAM are taken, with the CPU's stack pointer and the processor port `$01`. A turbo loader or an unpacker has done its work by then, so the bytes are the program as it runs. Nothing is recorded while it runs: what follows is static. The import note says the method: **vice** for a tape, **snapshot** for a VICE snapshot (`.vsf`). Without VICE a standard-loader tape is read block by block (**static**).

The processor port says what is mapped: with `$01 = $37`, BASIC ROM is at `$A000-$BFFF`, I/O at `$D000-$DFFF` and the KERNAL at `$E000-$FFFF`. A store to a ROM address is a store to the RAM under it. This tree does not ship the copyrighted ROMs: calls into them are named externals (`jsr CHROUT`), not function bodies.

## Functions: certain and probable

**Certain** functions are reached from a real entry point: the SYS target, the CPU's position when memory was taken, and the vectors at `$0314` / `$0316` / `$0318` (CINV, CBINV, NMINV) and `$FFFA` / `$FFFC` / `$FFFE`, including pointers the program plants with an immediate load and a store. From there `JSR`, `JMP` and branches are followed, and pointer tables those routines read.

**Probable** functions come from bytes no certain code reaches. A run of bytes is kept when it decodes cleanly to an `RTS`, `RTI` or `JMP` and scores enough: it touches hardware registers, calls the KERNAL or a certain function, its address appears elsewhere as a pointer. The finder is deliberately generous: an indirect `JMP`, an `RTS` dispatch or a jump table it can't read hides real routines, so it would rather offer a few that aren't.

So check a routine before you document it, most of all one nothing certain calls:

- Does it read like code: sensible registers, branches inside itself, a proper end?
- Or like data that happens to decode: sprite or character bytes, a table, text, long runs of `$00` or `$FF`, branches into the middle of other code?

**If it isn't code, don't document it.** Remove it with `delete_function(function, reason)`, saying what it is instead, e.g. "sprite data: 63-byte rows, read by the routine at $1A00 through $07F8". Its bytes are kept as data with your reason (`read_data` shows it), and `create_function` brings it back if it was code after all. It refuses when a documented routine reaches it; then, or whenever you aren't sure, flag it (`flag_for_review`) with that sentence so a person decides. Data a short branch skips is kept out of the instruction stream and recorded as data.

## Splitting and joining routines

The function finder's boundaries can be wrong both ways, and you can fix them as you go:

- **Two routines in one.** If a routine ends (an `rts`, `rti` or `jmp` that doesn't come back) and the bytes after it
  are a separate routine, something else calls or jumps there, or it does an unrelated job, cut it with
  `split_function(function, at="$xxxx")`. `at` is the address of the instruction where the second routine starts, and
  it must be the start of an instruction. The first part keeps its name; the second gets `func_xxxx` (or `new_name`).
- **One routine in two.** If a routine runs straight on into the next function with no `rts`/`jmp`, or branches into
  it, and nothing else calls the second part, join them with `merge_function(function)`. It refuses when something
  else calls the second part: then it really is a routine of its own, and the first part is a second way into it
  (common in 6510 code). Document just the first part's bytes and say that it carries on into the second.
- **A routine that was missed.** If code jumps or calls somewhere no routine starts and it isn't inside one (a jump
  table's entries, say), add it with `create_function(at="$xxxx", reason="how it's reached")`. It runs from `at` to
  its first `rts`, `rti` or `jmp`, or up to the next routine, and goes to the queue for its own write-up. If `at` is
  inside a routine, `split_function` is the tool instead.

Both pieces stay on the assembly track. A routine that was already documented goes back to being undocumented after a
cut or a join, because its write-up described the old bytes. If part of a routine isn't code, split it off and
remove that part with `delete_function`.

## Code that rewrites itself

Some routines store into their own instructions: `sta $E00D` / `sta $E00E` writing the two operand bytes of the `jmp $E2B7` at `$E00C`. Put a label on the instruction being patched and write the stores with it:

```asm
; jumps to the handler picked by Y from the table of addresses at $E00F
dispatch:
  lda HANDLERS,y
  sta patch+1        ; low byte of the jmp's target
  lda HANDLERS+1,y
  sta patch+2        ; high byte
patch:
  jmp first_handler  ; the target as the snapshot has it; the stores above replace it
HANDLERS = $E00F
```

## Code under the ROM

A program can switch the BASIC ROM (`$A000-$BFFF`) or the KERNAL (`$E000-$FFFF`) out and keep its own code in the RAM under it. A routine there is the program's, not the ROM's: the header's ROM names and descriptions don't describe it, and a `jsr`/`jmp` to one of the project's routines there uses the project's name.

## Labels

Import writes the memory map into `context.h` and the project symbols, and the disassembly uses those names.

- Processor port `$00` / `$01`, zero page and the usual page-2 and page-3 locations.
- VIC-II `$D000–$D02E` and its mirrors through `$D3FF`. SID `$D400–$D41C` and its mirrors through `$D7FF`. Colour RAM `$D800–$DBFF`. CIA1 `$DC00–$DC0F` and CIA2 `$DD00–$DD0F`, each register named, and their mirrors.
- Default screen RAM `$0400`.
- The KERNAL jump table `$FF81–$FFF3` (`CHROUT` at `$FFD2`, `GETIN` at `$FFE4`, `SETLFS`, `SETNAM`, `LOAD`, `SAVE`).
- BASIC and KERNAL ROM routines and data tables, with a one-line description.

Those ROM names and descriptions come from sk6502 (Richard Dymond, ISC). sk6502's control file derives the annotations from Lee Davison's 2012 disassembly. I/O and zero-page names are the standard map. The header states the assumed banking: **`$01 = $37`**.

## Reading memory

`read_data("$7322")` shows the bytes as they were once the program had loaded, then the same bytes as 16-bit words, low byte first: `22 73` is the word `$7322`. Under that it says which routine holds the first byte, or that the address is between routines (most likely a variable or a table). It also says when the byte is an operand inside an instruction, which means some code changes that instruction. Last, it lists every routine that reads, writes or indexes into the bytes shown.

Trust what it shows. Don't work the bytes out again from memory, and don't read the same address twice in a row. If what you thought and what `read_data` says disagree, `read_data` is right. A value is only what was there when loading finished, so don't build a routine's meaning on it.

## Small routines

Many routines are two or three instructions: `lda $7322` then `rts` returns a variable, `sta $7322` then `rts` sets it, and `jmp $8000` passes control on. Write one comment saying what it gets, sets or passes on, name the variable if you can tell what it holds from the routines that use it, and submit. Don't spend more than a few calls on a routine like that; the routines that use the variable are where its meaning becomes clear, and you can rename it then.

To name a variable for everyone, either call `rename_symbol("$7322", "wLettersLeft")` or add `#define wLettersLeft 0x7322` to the header with `edit_context`. Do one, not both: either way the name becomes a label straight away, every routine can use it, and `read_data` shows it. `get_function` also takes an address: `get_function("$8929")` gives the routine that starts there, or tells you which routine it is inside.

Routines come to you bottom-up: a routine is handed out once everything it calls, jumps or branches into, or runs on into is documented, so its claim lists those with how it reaches each one, its name and its comment. If it says the routine runs on into the next one, see Splitting and joining routines above. Use those names and what they say; don't reopen a documented routine to work it out again.

## Documenting a routine

`claim_function(track="asm")`. The routine is py65 assembly that rebuilds the program's bytes. Guide `asm` lists the six checks; on this platform:

- `lda #$00`, `sta VIC_BORDERCOLOR`, `jsr CHROUT`, `bne loop`, `.byte` / `.word`.
- Name an address with `wName = $033C`. Hardware and KERNAL/BASIC calls use the map's names.
- A name under `$100` works whether the program uses it as zero page (`lda $1E,x`) or absolute (`lda $001E,x`): it takes whichever form the snapshot has there.
- A branch or jump to an address outside the routine: define its name, `wait_key = $5962`, and write `beq wait_key`. A label (`wait_key:`) only marks an instruction you write in this routine, so one placed after the last instruction lands there, not at $5962. If the bytes at that address belong to no routine and run on into this one, the split cut it short: `create_function` there, then `merge_function` this routine, and document it whole.
- A name can take an offset: `lda TABLE+1,y` for the high byte of a table of addresses, `sta patch+1` for the operand of an instruction the routine rewrites.
- `.org`, `.include` and macros are refused.
- A comment before the routine says what it does. The label is not `func_....`: write the real name as the label in the same compile, and it becomes the routine's name when it's documented. There's no need to `rename_symbol` the routine first.

cc65 is not used to match these programs. A C toolchain is not required to import.
